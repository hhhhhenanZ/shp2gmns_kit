# shp2gmns_kit: MPO planning network → GMNS → TAPLite

Convert a regional planning model's highway network and trip tables (shapefile / Emme / Cube / TransCAD
exports) into [GMNS](https://github.com/zephyr-data-specs/GMNS) `node.csv`, `link.csv` and demand files,
check every value against the agency's own results, and run the same demand in the open
[TAPLite](https://github.com/asu-trans-ai-lab/TAPLite) assignment.

This repository shows **one case: CMAP, the Chicago Metropolitan Agency for Planning**, using its trip-based
travel demand model (ON TO 2050 update, conformity cycle c25q4, scenario 100 = 2019 base year), for the PM peak
period (4–6 pm). The code for two other networks (NVTA and SCAG) is kept in the kit so the same steps can be
repeated on them. See [Other networks](#other-networks-the-general-kit).

## Interactive report

**[Open the CMAP report (map, tables, results)](https://hhhhhenanz.github.io/shp2gmns_kit/data/output/cmap/report/CMAP_report.html)**:
CMAP's PM assignment on every road link, with the conversion checks and the first TAPLite results. It needs no
install; the map library and basemap load from the internet.

| Document | Content |

| [`FIELD_PROVENANCE.csv`](data/output/cmap/FIELD_PROVENANCE.csv) | Every output column: rule, source, status, unit |

## Gate run folders (CMAP, PM)

One command builds a run folder from the CMAP files, with one checked file per gate (L0-L3) and a manifest
(sha256 and producing script for every file). The run folder lives outside this repository.

```bat
python code\run_gates.py --region region.cmap.yaml --run ..\cmap_2019_pm --steps raw convert publish demand L0 L1 L2 L3build
:: run TAPLite in ..\cmap_2019_pm\04_assignment (engine: region.cmap.yaml > assignment > engine), then
python code\run_gates.py --region region.cmap.yaml --run ..\cmap_2019_pm --steps L3 manifest
```

The finished gate files of the two runs are in [`gate_runs/`](gate_runs/): `cmap_2019_pm` (CMAP, PM) and `scag_2050plan` (SCAG, AM). Each has a README that states the level reached, every L file, the manifest (sha256 of every file, including the large ones kept outside the repository) and the rerun record.

SCAG: `python code\run_gates.py --region region.yaml --data-root <SCAG kit with data\> --run <SCAG>\scag_2050plan`.

The demand step stops after a time budget and resumes; exit code 2 means run it again. Layout, rules and the
identity each gate checks: [`code/gates/README.md`](code/gates/README.md). Settings that matter for the gates are
in `region.cmap.yaml`: `demand > min_volume` (0.01; 0 = full tables), `taplite_vdf` (BPR for now, CMAP fd1-fd8 kept
in `cmap_*` columns; bus preload not included) and `assignment` (8 GB limit; car classes merged).

## Results so far (CMAP, PM)

**Conversion (level 1): complete.** 20,190 nodes, 3,649 zones, 55,005 directed links (none dropped), 8 demand
classes, 3.48 M vehicle trips. 29 gates pass, 0 fail. Where CMAP stored a value, the conversion reproduces it
exactly: volume, congested time, lanes, free-flow time and SOV demand. Trips between zones match the trips leaving
CMAP's centroids to 0.990.

**Assignment test (level 2): first run, preliminary.** TAPLite assigned the full PM demand on this network with
BPR (α 0.15, β 4), no tolls, 10 iterations (gap 0.18 %). Results against CMAP's own PM assignment, all links:

| Measure | TAPLite | CMAP | Ratio |
|---|---|---|---|
| VMT (vehicle-miles) | 31.0 M | 33.5 M | 0.93 |
| VHT (vehicle-hours) | 847 k | 1,193 k | 0.71 |
| Delay (vehicle-hours) | 34 k | 312 k | 0.11 |
| Average speed (mph) | 36.6 | 28.1 | 1.30 |
| Link volume R² (road links) | | | 0.93 |

Volumes match; BPR (0.15, 4) adds far too little delay compared with CMAP's own volume-delay functions. The
assignment inputs, the TAPLite build, the run scripts and the evaluation are in
**[city-tensor/cmap_ta_bpr_allmodes](https://github.com/hhhhhenanZ/city-tensor/tree/main/cmap_ta_bpr_allmodes)**

## Run (CMAP)

```bat
pip install -r requirements.txt
python code\check_inputs.py --region region.cmap.yaml
python code\main_convert.py --region region.cmap.yaml --periods PM
```

The result is `data/output/cmap/network/PM/node.csv` and `link.csv`, plus `demand/PM/<mode>_PM.csv`. Read
`data/output/cmap/CONVERSION_REPORT.md` and `checks/gate_report.csv` first. All rules, units and references are
in `region.cmap.yaml`.

| Item | Rule |
|---|---|
| Inputs | PM shapefiles `emme_links`/`emme_nodes` + `attribs_p7.txt` (capacity, speed and free-flow time are only there) |
| Nodes | Emme ids kept; zones are 1–3649; EPSG:26771 (US ft) → EPSG:4326 |
| Capacity | `@emcap`, vehicles/hour/**lane**. VDF 6 (connector) and 7 (toll link): CMAP value is 0, so a **99,999 placeholder** with alpha 0 (`region.cmap.yaml > vdf > no_capacity_links`, CMAP only) |
| Free-flow | `vdf_fftt = @ftime` (min), as given, including CMAP's free-speed rules |
| VDF | CMAP codes 1–8 in `vdf_code`; CMAP functions in `parameters/vdf_parameters.csv`; the TAPLite form for 1–5, 8 is chosen in the replay step |
| Demand | Built as CMAP's `ttables.mac` builds the PM tables; 8 classes, vehicles per 2-hour period; cells ≤ 0.01 not written |
| Units out | length m, free_speed km/h (kit convention), with miles and mph kept in `vdf_length_mi`, `vdf_free_speed_mph` |

Without pyogrio / pyproj, the converter falls back to a built-in shapefile reader and reprojection (checked to
0.0 m median against the pyproj result).

| Path | Contents |
|---|---|
| `CONVERSION_REPORT.md` | sources, everything not found in the SCAG files, checks against SCAG's loaded network, decisions to confirm |
| `FIELD_PROVENANCE.csv` | every output column: rule, source, status (`source field`, `documented rule`, `derived`, `external input`, `not found`) |
| `parameters/` | `zone_centroids.csv`, `period_factor.csv`, `vdf_parameters.csv`, `on_ramp_function_check.csv`, `access_rule_check.csv`, `mode_type_by_period.csv` |
| `network/<P>/` | `link.csv`, `node.csv`; `network/link_geometry.csv` holds the WKT for all periods and `network/link_excluded.csv` lists what was left out and why |
| `demand/<P>/` | `DA_<P>.csv` ... `SR3_NONHOV_<P>.csv`; only cells above `demand > min_volume` are written |

Read the "Not found" and "Decisions" sections of `CONVERSION_REPORT.md` before using the
network: tolls, link-specific truck PCE, bus preload and two occupancies are not in the
files provided, and the on-ramp function choice is open.

`link.csv` carries no geometry column by default. The WKT lives in
`network/link_geometry.csv` (`link_id, org_link_id, dir_side, crs, geometry`), written once for
every period - join on `link_id`. 110 of the 173,701 links have a WKT longer than Excel's
32,767-character cell limit (the longest is 162,869 characters, a 35-mile highway with 7,148
vertices), so a geometry column makes link.csv unreadable in Excel and halves its size for
nothing. TAPlite reads the column as optional and only echoes it into `link_performance.csv`.
Set `output > geometry_separate_file: false` to put it back in `link.csv`.

`demand > min_volume` in `region.yaml` is a floor on the trip tables: a cell is written only
if it carries more than that many vehicle trips. It is set to **0.01**, which keeps about
99.2% of SCAG's trips in 14.5% of the cells - the matrix is a long tail of very small cells.
The Demand section of `CONVERSION_REPORT.md` gives the exact retained share per period and
mode. Set it to 0 to write every positive cell; raising it costs real trips (1 keeps 82%,
10 keeps 40%).

## Set up the two environments

The TAPlite kernel is a Windows, Python 3.11 package. Conversion needs GIS libraries
the kernel environment does not have, so the kit uses two environments.

| Environment | Python | Install | Used by |
|---|---|---|---|
| conversion | 3.10 or 3.11 | `pip install -r requirements.txt` | steps 1, 2, 4 |
| TAPlite | 3.11, Windows x64 | `pip install -r requirements-taplite.txt` | step 3 |

On a GIS-heavy machine, installing `geopandas` through conda is usually smoother:
`conda install -c conda-forge geopandas pyogrio`, then `pip install -r requirements.txt`.

The kit refuses to run the kernel unless its version and binary checksum match
`code/setup/taplite_pypi_lock.json`. This is deliberate: results are only comparable
across runs made with the same kernel.

## Quick start

**1. Put your data in place**

| Put this | Here | Rule |
|---|---|---|
| Network shapefile | `data/input/network/` | Copy every sidecar file: `.shp` `.dbf` `.shx` `.prj` (and `.cpg` if present) |
| OMX trip tables | `data/input/demand/` | One file per period. The file name must contain the period code, e.g. `i4_AM_Trips.omx` |

Inside each OMX file the kit expects six matrices named `<PERIOD>_<MODE>s`:
`AM_SOVs  AM_HV2s  AM_HV3s  AM_COMs  AM_TRKs  AM_APVs`.

**2. Edit `region.yaml`** — at minimum the shapefile name, then any field names that
differ (see the next section).

**3. Run the steps** from the kit folder

```bat
:: conversion environment
python code\check_inputs.py
python code\main_convert.py

:: TAPlite environment
python code\main_replay.py

:: conversion environment
python code\main_analyze.py
```

Add `--periods am` to any step to work on one period. Converting only the periods you
need saves time and disk: a single period's demand is about 400 MB for a network the
size of NVTA.

## Adapting it to another network

### Level 1 — edit `region.yaml` (most networks)

For a Cube network built on the same conventions (A/B nodes, `FTYPE`, `ATYPE`,
`CAPCLASS`, `SPDCLASS`, `{P}LANE`, `{P}LIMIT`, `{P}TOLL`), no code changes are needed.

| Section | What to set |
|---|---|
| `input`, `output` | Where your files are and where results go |
| `periods` | Start and end hour of each period. Keys must be `am`, `md`, `pm` or `nt` |
| `cube_fields` | Names of Cube's assigned volume, V/C, speed, capacity and limit fields. `{P}` stands for the period code. Use `overrides` for periods that break the pattern |
| `mode_volume_fields` | Cube's assigned volume for each of the six modes |
| `mode_types` | Value of time, PCE and occupancy for each mode and period |
| `conic` | Leave `alpha_table: derive` to fit parameters from Cube's output, or give a CSV to use a published table |
| `classification` | Labels for facility types and lane-use codes |
| `analysis` | Named corridors to report, as patterns matched against link names |
| `assignment` | Iteration counts to run, and processors |

Run `check_inputs.py` after every edit. It names each missing field.

### Level 2 — edit the converter (different Cube conventions)

Only if your shapefile uses different names or codes for the **input** network. These
files belong to the original converter; change values, not structure.

| If your network differs in… | Edit | Look for |
|---|---|---|
| Node, distance, area-type, facility-type or class field names | `code/src/dtalite4cube/cube2gmns/fieldnameconfig.py` | `cube_base_link_mapping` |
| Lane, limit or toll field pattern | same file | `cube_link_dependent_mapping` |
| Capacity or speed by class, lane-use codes | `code/src/dtalite4cube/cube2gmns/netconfig.py` | `capacity_class_dict`, `speed_class_dict`, `allowed_uses_dict` |
| OMX matrix names | `code/src/dtalite4cube/omx2csv.py` | `f"{time_period}_{lu.upper()}s"` |
| Period names other than am/md/pm/nt | converter and settings code | not supported without development |

## How the conical parameters are set

Cube's conical function has one free parameter, α; β follows from it so that travel
time equals free-flow time at zero volume.

```
t / t₀ = 2 + √( α²(1−x)² + β² ) − α(1−x) − β        β = (2α − 1) / (2α − 2)
```

Cube stores both V/C and the travel-time ratio for every link, so α is fitted directly
from Cube's own output, separately for each facility type × area type cell, pooling
all periods. A cell with too little congestion to determine α inherits its facility
type's value, and `alpha_by_ft_at.csv` says which cells did.

Cube measures congestion against a period capacity, `V/C = volume ÷ (hourly capacity × E)`.
The kit measures E from the same output and sets `vdf_plf = E ÷ H`, which makes TAPlite's
capacity basis identical to Cube's.

Centroid connectors get no delay (`vdf_type = 0`, `vdf_alpha = 0`, `vdf_beta = 1`),
matching Cube.

## Verified on NVTA

The kit was run end to end on the NVTA AM period and compared, file by file, with the
pipeline it was extracted from.

| Stage | Compared | Result |
|---|---|---|
| Input check | shapefile fields, OMX matrices | 10 of 10 pass |
| Parameters | `vdf_alpha` in 36 facility × area-type cells, and E | identical; 35 of 36 cells identified |
| Network | 144 `link.csv` columns on 49,329 links | 139 identical, including every column the assignment reads |
| Assignment, 1 iteration | volume, V/C, travel time, speed, VMT, VHT, PMT, PHT, six mode volumes | identical on all 49,329 links |
| Analysis | 10 tables | identical |

The five network columns that differ (`t0_hour`, `t2_hour`, `t3_hour`,
`qvdf_start_speed_mph`, `qvdf_end_speed_mph`) come from NVTA's QVDF calibration lookups,
which the kit leaves out because they are keyed to NVTA node numbers. They feed the
QVDF speed profile only. The conical assignment does not use them, and its results are
unchanged.

## Limits

- Period keys are limited to `am`, `md`, `pm`, `nt`. A period that crosses midnight is
  assigned from its start hour to 24:00 only.
- The kernel lock is for Windows x64, Python 3.11.
- NVTA's QVDF calibration lookups are not included. A QVDF study that needs them can
  point `NVTA_TAPLITE_RESOURCE_ROOT` at a folder holding them.
- The analysis compares against Cube's stored results. Cube reports volume-averaged
  results, so a small, one-sided difference near capacity is expected and is explained
  in the analysis rather than corrected.
